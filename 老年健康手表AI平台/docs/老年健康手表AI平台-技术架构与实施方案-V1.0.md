# 老年健康手表 AI 健康管理平台：技术架构与实施方案 V1.0

> 文档类型：产品技术架构 / AI 接入方案 / 工程实施路线  
> 版本：V1.0  
> 日期：2026-11-27  
> 当前状态：架构设计；尚未完成真实设备联调、算法验证或临床验证  
> 项目边界：基于已采购的第三方老年健康手表，建设数据接入、健康趋势分析、风险预警、AI 健康解释与家属协同平台。

---

## 0. 执行摘要

### 0.1 核心结论

本项目不应从“建设 11 个大模型 Agent”开始，也不应让大模型直接读取手表原始数据并判断老人是否患病。

推荐采用五层能力：

1. **设备数据层**：接入手表上报的实时快照、历史健康包、原始序列、告警、定位、设备状态和通话/SOS。
2. **算法与特征层**：先复用厂商已经提供的睡眠、心电、房颤、血氧算法；再建设本地数据质量、特征工程、个人基线和趋势计算。
3. **风险决策层**：由经过验证的阈值、规则、持续时间、信号质量和人工配置共同决定风险等级；保留规则版本和证据。
4. **AI 知识与解释层**：通过 RAG 检索可信健康知识，通过 LLM 将已确定的测量、趋势和风险事件解释为易懂的建议，不让 LLM 改写风险等级。
5. **应用与家属协同层**：呈现健康首页、预警中心、趋势、健康画像、健康计划、家庭守护和设备设置。

**第一阶段优先做可靠的数据闭环和可解释的规则预警，AI 第二阶段接入，模型训练与微调放到有足够数据和验证条件之后。**

### 0.2 当前资料带来的关键约束

- 手表使用二进制 Protobuf 上报与 JSON 上报混合协议，不是简单的 REST JSON 设备。
- 协议中有手表原始数据，也有厂商算法结果和外部终端转发数据，必须区分数据来源。
- 睡眠、心电、房颤、血氧已有厂商云算法入口；部分结果依赖前置数据聚合和特定时间窗口。
- 部分健康字段存在单位、测量来源或算法含义未确认的问题，不能直接作为风险判定输入。
- 手表配置下发后不一定能回读，平台需要维护“期望配置”和“下发状态”。
- 老年健康预警是高风险业务，必须让确定性规则和安全流程优先于生成式 AI。

### 0.3 目标产品定位

面向老人及其家属提供：

- 日常健康状态和数据完整性展示；
- 心率、血氧、血压、睡眠、活动等长期趋势；
- 经验证的异常提示与家属通知；
- SOS、跌倒等设备原生事件的快速处理；
- AI 健康报告、知识问答和健康计划辅助；
- 家属授权、设备配置、告警确认和历史追踪。

产品对外定位应是“健康监测、趋势提示和健康管理辅助”，不能仅凭消费级手表数据宣称疾病诊断或医疗级检测。

## 1. 项目范围与设计原则

### 1.1 V1 建设范围

| 模块 | V1 范围 | 优先级 |
|---|---|---|
| 设备接入 | 二进制/JSON 接口、设备绑定、在线状态、数据补传 | P0 |
| 协议解码 | Protobuf、帧校验、字段映射、单位归一化 | P0 |
| 数据存储 | 原始报文、测量数据、序列数据、算法结果、告警 | P0 |
| 厂商算法 | 睡眠、心电、房颤、血氧、长程心电任务 | P0/P1 |
| 数据质量 | 时间、缺失、异常值、有效佩戴、信号质量 | P0 |
| 风险引擎 | 规则、连续性、个体基线、数据可信度 | P1 |
| 家属通知 | SOS、跌倒、明确的高风险事件和通知确认 | P0 |
| 健康首页 | 真实可用数据、数据更新时间、状态解释 | P1 |
| AI 助手 | 健康摘要、趋势解释、知识问答、计划建议 | P2 |
| RAG | 指南、共识、设备说明书、健康教育资料 | P2 |
| 模型训练 | 监督学习/微调实验与验证体系 | P3，不是首期依赖 |

### 1.2 暂不纳入 V1 的能力

- 未经验证的肿瘤七项趋势、器官脉位映射等能力；
- 仅凭腕部 PPG 推断具体疾病；
- 将血糖、血钾、尿酸、血脂等协议字段直接作为临床可信检测结果；
- 由 LLM 自行判断是否急救、是否停药、是否调整药量；
- 在没有标注数据和参考设备的情况下训练所谓“老年疾病预测模型”；
- 直接复刻儿童方案中的 8 个专科 LoRA 和 11 Agent 集群。

### 1.3 设计原则

1. 数据可追溯：任何结论都能回溯到设备、原始报文、算法版本、规则版本和时间窗口。
2. 数据质量优先：无效数据、佩戴异常、信号质量不足时，宁可提示“数据不足”，不能输出确定结论。
3. 原始数据与算法结果分离：设备测量值、厂商算法输出、本地派生指标和 AI 文案分别存储。
4. 规则先于模型：安全阈值、SOS、跌倒、告警升级等由确定性逻辑控制。
5. AI 不越权：LLM 只能解释已确定的事实，不能更改风险等级或制造不存在的测量结果。
6. 模块化而不过度微服务化：初期用模块化后端和异步任务，规模增长后再拆分。
7. 场景隔离：儿童与老年人的用户档案、阈值、知识库和模型策略必须分域，不共享未经适配的判定规则。

## 2. 产品原型到技术能力的映射

原型是产品交互草图，不代表所有卡片的数据已经由当前手表协议支持。每个页面都必须绑定明确的数据源和能力状态。

| 原型模块 | 所需数据/服务 | 技术实现 | V1 建议 |
|---|---|---|---|
| 今日健康简报 | 最近测量、趋势、有效数据比例、已确认风险事件 | 日摘要服务 + AI 解释 | 先规则摘要，后接 AI |
| 健康状态/综合分 | 多维度指标、数据完整性、趋势 | 可解释评分服务 | 不建议先做黑盒单一分数 |
| 预警中心 | 设备告警、风险规则事件、SOS、跌倒 | 事件中心 + 仲裁规则 + 通知 | P0/P1 |
| 实时体征 | HR、BP、SpO₂、体温等及测量时间 | 最新测量查询 + 数据质量标签 | 只展示真实上报且单位已确认的指标 |
| 中医管理/慢病监控 | 经过验证的指标、病史、用药、生活方式 | 专项规则 + 知识库 | 先改为健康管理观察，不宣称脏腑检测 |
| 睡眠监测 | sleep_daily、sleep_segment、睡眠算法结果 | 厂商睡眠算法适配器 | P1 |
| 心理状态 | HRV、睡眠、用户主动问卷等 | 趋势与问卷结合 | 不可仅凭 HRV 诊断情绪/心理疾病 |
| 健康画像 | 长期测量、病史、生活方式、风险事件 | 用户健康档案 + 趋势聚合 | 分维度展示来源和可信度 |
| 活力三环 | 步数、活动时间、目标 | 活动统计服务 | 可先实现 |
| 健康趋势追踪 | 历史测量、个人基线、异常事件 | 时间序列分析 | P1 |
| 专家健康 | 风险事实、知识检索、解释文案 | RAG + LLM + 固定模板 | AI 不代替医生 |
| 养生管理计划 | 用户目标、生活方式、禁忌、已验证建议 | 规则模板 + AI 草拟 | 用户确认后执行 |
| 健康头条 | 审核过的健康内容 | 内容管理系统 | 与实时预警系统隔离 |
| 家人守护 | 家属关系、授权、通知、SOS 状态 | 家庭关系与权限服务 | P0 |
| 客服中心 | FAQ、设备问题、人工服务 | 知识库/客服系统 | 可后置 |

### 2.1 健康首页的展示约束

每张体征卡片至少要具备：

- 指标名称、数值、单位；
- 测量时间和数据来源；
- 有效/无效/待确认状态；
- 与个人基线相比的变化（只有基线有效时才显示）；
- 是否触发了规则事件；
- 数据缺失时明确展示“暂无有效数据”，不能用 0 填充。

原型中的 84.4 等综合分数，如果保留，必须公开其组成、权重、缺失数据处理和版本。首版更建议使用“健康状态概览 + 数据完整度 + 多维趋势”，避免制造看似精确但不可解释的健康分。

## 3. 总体技术架构

### 3.1 推荐架构图

~~~mermaid
flowchart TB
    W[老年健康手表] --> V[厂商设备平台]
    V --> G[设备接入网关 FastAPI]
    G --> R[原始报文归档]
    G --> D[协议解码与标准化]
    D --> Q[数据质量检查]
    Q --> DB[(PostgreSQL / TimescaleDB)]
    Q --> OBJ[(MinIO 原始波形/报告)]
    Q --> MQ[异步任务队列]

    MQ --> VA[厂商算法适配器]
    VA --> S[睡眠/心电/房颤/血氧/长程心电]
    S --> AR[(算法结果库)]

    DB --> FE[特征工程与个人基线]
    AR --> FE
    FE --> RE[规则风险引擎]
    RE --> RA[风险事件仲裁与状态机]
    RA --> ALERT[告警/通知服务]

    DB --> API[业务 API]
    AR --> API
    FE --> API
    RA --> API

    API --> APP[老人端/家属端]
    API --> CTX[AI 上下文服务]
    KB[(健康知识库 / pgvector)] --> RAG[RAG 检索]
    CTX --> RAG
    CTX --> LLM[统一模型网关]
    LLM --> LOCAL[本地推理服务]
    LLM --> CLOUD[授权后的云模型]
    RAG --> LLM
    LLM --> API
~~~

### 3.2 数据流与决策边界

- 接入网关负责收包、鉴权、快速应答和可靠投递，不承担健康判断。
- 解码层负责按官方 Protobuf 定义解析字段，不根据字段名称猜单位。
- 数据质量层负责缺失、重复、时间异常、无效佩戴和信号质量。
- 厂商算法适配器负责调用既有算法，保存输入窗口、请求摘要、响应、错误码和算法版本。
- 特征服务负责计算统计量、滑动窗口、个体基线和变化趋势。
- 风险引擎负责判断是否达到预先定义的规则条件。
- 风险仲裁负责多信号交叉、连续性、数据质量和事件去重。
- AI 服务负责解释、检索和生成建议，不拥有告警升级和风险定级权限。

### 3.3 初期服务部署形态

推荐采用模块化单体 + 独立后台 Worker：

- 一个业务 API 服务；
- 一个设备接入模块；
- 一个协议解码模块；
- 一个算法适配器模块；
- 一个风险/特征模块；
- 一个 AI/RAG 模块；
- 一个或多个异步 Worker；
- 一个数据库和一个对象存储。

模块可以先部署在同一应用中，但代码边界、数据模型和任务接口必须独立。只有当吞吐量、团队协作或故障隔离确实要求时再拆微服务。

## 4. 技术选型建议

| 层 | 推荐技术 | 选择理由 | 后续扩展 |
|---|---|---|---|
| 后端 API | Python + FastAPI | 与 Protobuf、算法、AI 生态衔接方便 | 多服务拆分 |
| 协议模型 | 官方 .proto + Protobuf | 字段、类型和枚举以协议定义为准 | 版本化 Schema |
| 数据校验 | Pydantic | 统一输入输出校验 | JSON Schema |
| 关系数据库 | PostgreSQL | 用户、设备、授权、事件、任务等事务数据 | 高可用 PostgreSQL |
| 时序数据 | PostgreSQL + TimescaleDB | 适合按设备/时间查询和聚合 | 分区、压缩、保留策略 |
| 缓存/队列 | Redis + Celery（初期） | 任务异步化、重试和缓存 | 高吞吐时 Kafka |
| 波形/大文件 | MinIO | PPG、ECG、长程心电和报告文件 | S3 兼容对象存储 |
| 向量检索 | pgvector | 初期减少独立向量数据库 | 数据规模增大后独立向量库 |
| 风险规则 | Python 规则模块 + 配置表 | 易审计、易回归、版本可控 | 复杂规则引擎 |
| AI 编排 | 自研 AI Context Service | 业务权限和工具调用边界清楚 | 可接入 Agent 框架 |
| 本地推理 | 现有本地推理平台统一 API | 复用模型服务、隐私策略和资源管理 | vLLM / llama.cpp 等引擎 |
| 监控 | Prometheus + Grafana + OpenTelemetry | 监控设备接入、算法任务和模型服务 | 日志平台 |

### 4.1 为什么不在首期部署 Kafka + Flink + Kubernetes

当前还没有真实设备规模、每台设备上报频率、日数据量和并发指标。此时引入完整流计算集群会增加部署、运维和故障定位成本。

首期用 PostgreSQL、Redis、Celery 和 Worker 足以验证完整业务链。出现以下情况再评估 Kafka/Flink：

- 大规模设备同时高频上报；
- 多个下游消费者需要独立消费同一数据流；
- 需要复杂实时窗口计算；
- 单一任务队列已无法满足吞吐或隔离要求。

不要为了架构图看起来先进而提前引入分布式组件。

## 5. 核心数据模型

建议先定义统一数据契约，后续不论接入第二家手表、血压计还是血糖仪，都进入同一规范层。

### 5.1 核心实体

| 实体 | 作用 | 关键字段 |
|---|---|---|
| user | 老人用户档案 | 年龄、性别、时区、病史、用药、紧急联系人 |
| family_relation | 家属授权关系 | user_id、guardian_id、权限、授权时间 |
| device | 设备档案 | device_id、IMEI、型号、固件、绑定状态 |
| raw_packet | 原始上报归档 | 原始字节、协议版本、接收时间、解析状态 |
| measurement | 结构化测量值 | 指标、数值、单位、时间、来源、质量 |
| signal_series | 连续序列索引 | PPG/RRI/ECG/SpO₂/ACC、对象存储地址 |
| vendor_algorithm_task | 厂商算法任务 | 类型、输入窗口、状态、重试次数 |
| vendor_algorithm_result | 厂商算法输出 | 原始响应、解析结果、算法版本、有效性 |
| derived_feature | 本地派生特征 | 特征名、值、窗口、算法版本 |
| personal_baseline | 个体基线 | 指标、统计区间、样本量、质量、版本 |
| risk_rule | 风险规则配置 | 适用人群、条件、持续时间、版本 |
| risk_event | 风险事件 | 等级、证据、触发原因、状态、处理人 |
| notification | 通知记录 | 渠道、接收人、送达状态、确认状态 |
| device_setting | 设备期望配置 | cmd_key、参数、下发状态、响应码 |
| knowledge_document | 知识来源 | 文档版本、来源、适用范围、审核状态 |

### 5.2 统一测量数据结构

每一条测量记录至少包含：

~~~json
{
  "user_id": "user_x",
  "device_id": "device_x",
  "metric": "spo2",
  "value": 97,
  "unit": "%",
  "measured_at": "2026-11-27T01:20:00Z",
  "received_at": "2026-11-27T01:20:03Z",
  "source_type": "watch_health_data",
  "source_field": "bxoy_data.agv_oxy",
  "quality_status": "pending_validation",
  "quality_flags": [],
  "protocol_version": "watch-protocol-v1"
}
~~~

这里的 97 只是结构示例，不代表当前协议已确认该字段单位和有效性。正式数据必须由协议适配器根据字段证据填写，不能由 AI 推测。

### 5.3 来源和可信度分层

统一使用来源类型：

- device_raw：设备原始上报；
- device_alarm：设备本身生成的告警；
- vendor_algorithm：厂商云算法；
- platform_rule：我方规则引擎；
- platform_ml：我方经过验证的机器学习模型；
- ai_generated：AI 生成的解释或建议。

AI 生成内容永远不能伪装成测量数据或算法检测结果。

### 5.4 时间、单位和幂等

- 数据库存储统一使用 UTC 时间，用户展示时转换为用户配置的时区。
- 原始时间字段和协议时区字段必须保留，不能只存转换后的本地时间。
- 所有历史数据支持补传、乱序和重复到达。
- 建议使用设备 ID + 数据类型 + 测量时间 + 序列/分片标识构造幂等键；不能只依赖 HTTP 请求 ID。
- 同一条数据重复到达时执行幂等更新，不重复触发通知。
- 每个指标有独立单位字典和换算函数，严禁跨上行/下行复用单位换算。

## 6. 数据处理与算法实现逻辑

### 6.1 设备接入流程

1. 接收设备 HTTP 请求。
2. 校验路径、设备身份、请求大小和协议帧结构。
3. 保存原始报文及接收元数据。
4. 按 magic、长度、opt、Protobuf 消息类型解码。
5. 对每个字段执行类型、单位、时间和枚举校验。
6. 生成标准测量、序列、告警和设备状态事件。
7. 通过幂等键写库。
8. 创建后续算法和特征计算任务。
9. 按厂商协议要求返回应答字节。

接入接口必须快速结束。算法请求、AI 生成、长程心电处理和通知发送都放入后台任务。

### 6.2 数据质量检查

建议每条测量带以下质量标记：

- valid：字段、单位、时间和质量均满足使用条件；
- pending_validation：字段存在，但单位、来源或测量能力尚未确认；
- invalid：明显无效或违反协议约束；
- incomplete：缺少必要数据；
- low_signal_quality：信号质量不足；
- not_worn：设备未佩戴；
- stale：数据过期；
- corrected：经过明确记录的纠正或换算。

质量检查不能简单把异常值删除。应保留原始数据，并记录过滤原因，便于复盘。

### 6.3 厂商算法调度

每种算法独立建立任务处理器：

| 任务 | 触发条件 | 前置检查 | 失败处理 |
|---|---|---|---|
| sleep | 当天和前一天睡眠数据齐备 | 睡眠原始串、RRI、日期窗口 | 延迟补算 |
| ecg | 单次 ECG 分片收齐 | 同一 time_stamp 合并、信号有效性 | 不落结论，重试或待人工 |
| af | 当日 RRI 聚合完成 | 至少 10 个有效点 | 数据不足不调用 |
| spo2 | 睡眠结果可用 | 仅截取实际睡眠窗口 | 等待睡眠结果后补算 |
| long_ecg | 多导联测量完成 | 文件、时长、体积和时间范围 | 异步重试/人工核查 |

算法任务表要记录：

- task_id、user_id、device_id；
- algorithm_type；
- input_window_start/end；
- input_data_version；
- request_payload_hash；
- status：pending/running/succeeded/failed/insufficient_data；
- retry_count、next_retry_at；
- vendor_return_code；
- vendor_algorithm_version；
- result_id。

相同输入窗口和数据版本不能无限重复提交。算法服务不可用时，不阻塞其他业务，也不写入伪造的默认结果。

### 6.4 个人基线

个人基线是健康趋势判断的辅助参照，不是医学诊断标准。

建议分阶段：

- 冷启动：没有足够历史数据时，使用经过审核的人群参考和绝对安全阈值；同时标注“个人基线尚未建立”。
- 建立期：积累连续、有效、佩戴质量合格的数据。
- 稳定期：按指标采用不同时间窗口和统计方法。
- 更新期：滚动更新，但保留历史基线版本。

基线可使用中位数、分位数、MAD 等稳健统计方法；不能所有指标都套用同一个 28 天窗口。

注意：不能让长期恶化的数据不断进入基线，最终把异常“学习成正常”。需要设置基线冻结、漂移审查和人工复核机制。

### 6.5 风险规则与仲裁

每条风险规则必须明确：

- 适用人群与排除条件；
- 指标来源及有效状态；
- 绝对阈值和/或个体变化条件；
- 持续时间、复测要求；
- 多信号组合条件；
- 风险等级；
- 通知对象和升级策略；
- 规则版本、依据来源、审核人。

风险判定流程：

~~~mermaid
flowchart TD
    A[新测量或厂商算法结果] --> B{数据质量是否合格}
    B -- 否 --> C[记录数据不足/信号质量问题]
    B -- 是 --> D[匹配适用风险规则]
    D --> E{是否满足触发条件}
    E -- 否 --> F[仅更新趋势与基线]
    E -- 是 --> G[检查持续时间/复测/多信号]
    G --> H{证据是否足够}
    H -- 否 --> I[观察或请求复测]
    H -- 是 --> J[生成带证据的风险事件]
    J --> K[风险仲裁与去重]
    K --> L[通知老人/家属/服务人员]
    L --> M[确认、处理、关闭与审计]
~~~

紧急事件不能被普通趋势规则延迟。SOS、设备原生跌倒告警等应有独立快速通道；但也要区分“设备上报了事件”和“事件已经人工确认”。

## 7. 风险等级与通知设计

风险级别建议采用产品级事件分类，而不是由大模型自由生成：

| 级别 | 含义 | 处理策略 |
|---|---|---|
| 紧急 | SOS、设备跌倒事件或经审核的紧急规则命中 | 立即通知指定联系人，显示事件时间和可用位置 |
| 高 | 经过验证的异常条件满足且证据充分 | 尽快通知家属，提示复测/及时寻求专业帮助 |
| 关注 | 持续趋势偏离或多个非紧急信号共同变化 | 纳入健康简报和计划 |
| 观察 | 单次波动、证据不足或需要更多数据 | 不进行高强度打扰，继续观察 |
| 数据异常 | 未佩戴、信号差、设备离线、数据缺失 | 提醒检查设备，不伪装成健康异常 |

以上是软件事件级别框架，不是医学阈值定义。具体数值和临床处置文案必须由适用地区的临床专业人员审核，并依据设备实际验证结果确定。

### 7.1 预警状态机

建议状态：

- detected：规则首次命中；
- pending_confirmation：等待复测或其他证据；
- notified：已发通知；
- acknowledged：家属/服务人员已确认；
- in_progress：处理中；
- resolved：已解决；
- false_positive：确认误报；
- expired：超时关闭但保留记录。

告警必须支持去重、冷却时间、升级、确认和审计。不能通过简单的“同类型告警每天只发一次”掩盖新的严重事件。

### 7.2 通知渠道

采用 Notification Provider 抽象：

- App Push；
- 短信；
- 电话/语音外呼（需要合法合规的服务商）；
- 家属端站内消息；
- 服务人员工作台。

渠道是否可用、是否送达、是否确认必须分别记录。不能把“调用推送接口成功”当成“家属已经看到”。

## 8. AI 与 RAG 的正确接入方式

### 8.1 AI 适合做什么

| 场景 | AI 作用 | 是否建议 |
|---|---|---|
| 每日健康简报 | 把已确定的趋势和事件解释成人话 | 推荐 |
| 指标解释 | 解释 HRV、睡眠、血氧等概念 | 推荐 |
| 健康问答 | 从审核知识库检索并回答 | 推荐 |
| 家属周报 | 汇总一段时间的有效趋势和已确认事件 | 推荐 |
| 生活方式计划 | 根据用户目标、禁忌和知识库草拟建议 | 推荐，需用户确认 |
| 异常风险定级 | 直接让 LLM 看数字决定危险程度 | 禁止作为最终决策 |
| 疾病诊断 | 根据手表数据诊断疾病 | 不纳入产品能力 |
| 药物调整 | 自动建议停药、加量、换药 | 禁止 |

### 8.2 RAG 是否需要

**需要，但不应该在第一阶段阻塞设备接入和规则预警。**

RAG 解决的是“AI 应该依据什么可信知识解释问题”，不是“如何从原始传感器算出医学风险”。

建议知识库按内容分区：

1. 老年健康管理与慢病随访指南；
2. 心血管健康、血压管理和房颤相关权威指南；
3. 睡眠、呼吸和跌倒预防资料；
4. 老年营养、运动、用药安全与生活方式资料；
5. 急救与紧急情况的官方指导；
6. 手表说明书、测量原理、校准方法和已验证能力；
7. 平台产品帮助、设备故障和常见问题。

每份文档必须保留：

- 来源机构和原始链接；
- 文件名称、发布日期、版本；
- 适用地区、年龄和人群；
- 生效/失效时间；
- 审核状态、审核人；
- 证据级别和适用范围。

### 8.3 RAG 检索链路

~~~mermaid
flowchart LR
    Q[用户提问或报告任务] --> I[意图与权限检查]
    I --> T[读取结构化健康数据工具]
    I --> R[检索健康知识库]
    R --> F[重排与证据过滤]
    T --> C[AI 上下文组装]
    F --> C
    C --> L[LLM 生成结构化解释]
    L --> V[事实、来源、合规校验]
    V --> O[健康解释/家属简报]
~~~

建议首期使用 PostgreSQL + pgvector，并结合全文检索。只有知识规模和检索性能确实需要时才引入独立向量数据库。

### 8.4 AI 不直接读取数据库

给 LLM 提供受控工具，而不是数据库连接：

- get_user_profile：读取经授权的基本档案；
- get_latest_measurements：获取最新有效测量；
- get_health_trend：获取指定时间范围趋势；
- get_vendor_algorithm_result：获取厂商算法结果及有效性；
- get_risk_events：读取风险事件及其状态；
- search_health_knowledge：检索已审核知识；
- draft_health_summary：生成待审核的健康简报；
- draft_care_plan：生成待用户确认的健康计划。

工具服务需要做用户身份、家属授权、数据范围和审计检查。模型不能通过任意 SQL 绕过权限。

### 8.5 LLM 结构化输出

AI 输出至少应包含：

- summary：简要解释；
- facts：使用了哪些真实测量和趋势；
- evidence：知识来源和版本；
- uncertainty：数据不足、设备限制和不确定性；
- suggested_actions：低风险、可执行的健康管理建议；
- escalation：是否存在规则引擎已经判定的风险事件；
- disclaimer：适用的健康提示边界。

risk_level 必须从风险引擎读取，LLM 不允许自行生成或覆盖。

## 9. 本地模型、云模型与现有推理平台对接

### 9.1 推荐采用统一模型网关

业务服务不直接绑定某个模型、厂商 API 或推理引擎。统一模型网关负责：

- 模型选择和版本管理；
- 本地/云端路由；
- 用户数据脱敏；
- Token、延迟、错误和成本记录；
- 超时、限流和重试；
- local-only 隐私策略。

### 9.2 与现有本地 AI 推理平台的关系

现有本地 AI 推理引擎项目作为“模型基础设施”，本老年健康平台作为“业务应用”。

~~~mermaid
flowchart TB
    A[老年健康平台] --> B[AI Context Service]
    B --> C[统一模型网关]
    C --> D[现有本地 AI 推理平台]
    D --> E[本地 LLM]
    D --> F[本地 Embedding/Reranker]
    C --> G[授权云模型 API]
    H[知识库] --> F
~~~

建议通过 OpenAI-compatible API 或稳定的内部 API 调用本地模型，业务侧不关心模型运行在 Ollama、llama.cpp 还是 vLLM。

如果数据策略要求本地处理，资源不足时只能排队、拒绝或请求授权，不能静默切换云端。该原则与现有本地推理平台的 local-only 设计保持一致。

### 9.3 模型任务分配

| 任务 | 推荐处理方式 |
|---|---|
| 心率、血压、血氧数值阈值 | 规则引擎 |
| HRV、睡眠、活动特征 | Python 数值计算/信号处理 |
| 厂商睡眠/心电/房颤/血氧 | 厂商算法 API |
| 健康知识检索 | Embedding + RAG |
| 健康摘要、解释、问答 | LLM |
| 复杂时序模式识别 | 有标注数据后评估专用 ML 模型 |
| 预警升级、SOS | 确定性状态机和通知系统 |

## 10. 是否需要训练模型或微调

### 10.1 V1 不需要训练大模型

目前没有足够证据证明训练或 LoRA 微调能够改善当前产品的核心问题。首先要建立：

- 稳定的设备数据；
- 可靠的测量单位和来源；
- 厂商算法基准；
- 临床参考设备或专业标注；
- 可复现的规则评估数据集；
- 误报、漏报和数据缺失记录。

没有这些基础，微调只能让模型更像“专业地说话”，并不能证明其判断更准确。

### 10.2 未来可以训练哪些模型

| 模型方向 | 输入 | 目标 | 前置条件 |
|---|---|---|---|
| 信号质量模型 | PPG、ECG、ACC | 判断信号是否可用 | 有效/无效信号标注 |
| 个体异常检测 | HR、HRV、睡眠、活动 | 发现偏离个人模式的变化 | 足够长的连续随访 |
| 跌倒识别 | ACC、陀螺仪、事件窗口 | 识别疑似跌倒模式 | 真实跌倒/非跌倒样本 |
| 睡眠辅助模型 | 睡眠序列、RRI、体动 | 辅助睡眠阶段估计 | PSG 或可信参考标注 |
| 报告文本模型 | 已审核的结构化报告 | 提高文本一致性 | 专家审核语料 |

### 10.3 LoRA 微调的适用范围

未来如果发现通用 LLM 在报告格式、固定术语、工具调用或特定问答上存在可量化的不足，可以考虑 LoRA。

但以下情况不应该靠 LoRA 解决：

- 设备采样错误；
- 单位不明确；
- 测量原理不可靠；
- 信号质量差；
- 风险阈值没有依据；
- 缺乏医学参考标准。

**优先顺序：规则和特征工程 → RAG 与结构化工具 → 评估数据集 → 专用 ML → 必要时 LLM 微调。**

## 11. 安全、隐私与医疗边界

### 11.1 数据安全

- 全链路 HTTPS/TLS；
- 设备凭证、厂商算法账号密码使用 Secret 管理，不进入日志；
- 健康数据、身份信息和定位信息按敏感数据保护；
- 数据库和对象存储加密、备份和访问审计；
- 老人和家属采用明确授权关系；
- 家属只能访问被授权的数据和操作；
- AI 请求只传完成任务所需的最小数据；
- 默认不把原始 ECG/PPG 上传给外部通用模型；
- 设计数据导出、更正、删除、撤销授权和保留期限。

### 11.2 健康产品边界

在正式上线前，需要根据实际销售地区和功能定位，评估适用的个人信息保护、健康数据处理、医疗器械及广告宣传要求。

对外文案应区分：

- 设备测量值；
- 厂商算法筛查结果；
- 平台趋势分析；
- AI 健康管理建议；
- 医疗机构诊断。

不得把“风险提示”包装成“确诊”，也不得把算法分数包装成临床准确率。

## 12. 实施路线与 Gate

### Phase 0：设备与协议验证

交付：

- 真实设备样本和连续上报记录；
- 全部字段、单位、采样频率、时间戳核查表；
- 厂商算法 API 真实请求/响应样本；
- SOS、跌倒、离线、补传和配置下发测试；
- 未确认字段清单及厂商书面答复。

Gate：核心数据能够被稳定接收、正确解码、去重和追溯；关键健康字段有明确单位和来源。

### Phase 1：数据底座与产品基础功能

交付：

- 设备接入网关；
- 原始报文归档和标准化数据模型；
- 设备、用户、家属授权；
- 最新体征、历史趋势、设备状态；
- 原生告警、SOS、跌倒事件；
- 设备配置下发和状态跟踪。

Gate：数据完整性、重复处理、异常包、断网补传和告警通知通过测试。

### Phase 2：算法与风险引擎

交付：

- 睡眠、心电、房颤、血氧厂商算法适配；
- 异步任务、失败重试和结果版本化；
- 信号质量和个体基线；
- 风险规则、仲裁、告警状态机；
- 规则依据、证据和审计看板。

Gate：每条预警可以解释触发条件、证据窗口、数据质量、规则版本和处理状态；完成专业人员审核。

### Phase 3：RAG 与 AI 健康助手

交付：

- 审核知识库；
- RAG 检索和引用；
- 结构化健康数据工具；
- 每日/每周健康简报；
- 家属问答和健康计划草稿；
- AI 安全评估与权限审计。

Gate：AI 不编造测量、不更改风险等级、知识来源可追溯、权限不能越界。

### Phase 4：机器学习与个性化优化

交付：

- 脱敏标注数据集；
- 信号质量和异常检测模型实验；
- 训练/验证/外部测试划分；
- 专业评估和灰度发布；
- 模型版本、回滚和持续监测。

Gate：新模型在独立测试集上相对基线有明确收益，且没有不可接受的漏报和误报。

## 13. 核心验收指标

| 维度 | 指标 |
|---|---|
| 接入可靠性 | 接收成功率、解码成功率、丢包/重复率 |
| 数据质量 | 有效测量比例、单位未知比例、信号质量分布 |
| 时效性 | 上报至落库延迟、算法任务等待时间、告警通知延迟 |
| 算法稳定性 | 厂商算法成功率、失败重试率、输入完整率 |
| 风险质量 | 灵敏度、特异度、阳性预测值、误报率、漏报率 |
| 通知质量 | 送达率、确认率、升级完成率 |
| AI 质量 | 事实一致性、引用正确率、无依据结论率、拒答合规率 |
| 系统质量 | API 可用性、任务积压、恢复时间、备份恢复结果 |

风险指标必须基于有参考标准的独立数据集，不能用模型自己生成的标签评估自己。

## 14. 当前必须向手表厂商确认的问题

1. SpO₂ 字段的准确单位、有效范围和质量标记。
2. 血压测量是袖带、脉搏波估算还是其他方式；是否需要个体校准；有无独立验证报告。
3. 血糖、血钾、尿酸字段的实际测量来源、单位、算法原理和验证资料。
4. 体脂、BMI、BioZ 字段是否来自手表本体，测量时是否需要特定接触条件。
5. 体温 type=2 的正式语义、有效条件和数据单位。
6. HRV、RRI 的采样率、单位、窗口长度和伪差处理方式。
7. PPG、ECG、加速度数据的采样率、时间戳、分片规则和丢包补传机制。
8. protobuf DateTime.time_zone 是否应参与本地时间转换。
9. 电量字段 0～9 与 0～100 的冲突应以哪个固件版本为准。
10. CRC 算法、失败应答码和设备重传策略。
11. SOS 告警是否保证包含定位；无定位时的补充机制。
12. 厂商算法结果枚举、版本更新策略、API 限流、超时和数据保留周期。
13. 设备配置下发的成功回执是否代表设备实际生效，有没有设备端确认机制。
14. 心电、房颤、血氧、睡眠算法的适用人群、验证报告和已知限制。

---

## 15. 最终架构决策

| 决策项 | V1 推荐结论 |
|---|---|
| 产品方向 | 老年健康监测、趋势分析、预警和家属协同 |
| 数据接入 | 严格按现有双向协议实现 |
| 后端架构 | Python/FastAPI 模块化单体 + Worker |
| 数据存储 | PostgreSQL/TimescaleDB + MinIO |
| 异步任务 | Redis + Celery，任务状态落库 |
| 算法 | 优先复用厂商算法，本地做质量控制和特征工程 |
| 风险判定 | 确定性规则 + 个体基线 + 风险仲裁 |
| AI | 统一模型网关 + 结构化工具调用 |
| RAG | 需要，首期后置，不阻塞设备和风险链路 |
| 大模型训练 | V1 不训练 |
| LoRA 微调 | V1 不做，后续有明确数据和收益再评估 |
| 多 Agent | 暂不建设 11 Agent，先模块化能力服务 |
| 本地推理 | 复用现有 AI 推理平台 |
| 部署 | 初期 Docker Compose，按规模升级 |
| 医疗边界 | 健康趋势与筛查提示，不做无依据诊断 |

**最终原则：先让数据可信，再让风险可信，最后让 AI 把可信的结果解释得更好。**
